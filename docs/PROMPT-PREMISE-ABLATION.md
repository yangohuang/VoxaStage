# 复杂回答消融：词表注入与前提约束

2026-10-16。针对[上一轮复杂回答失败](REPLY-QUALITY-BASELINE.md)做同模型文字实验：单独切换领域词表和一般性前提约束，检查项目名提示是否影响模块归属与诊断建议。**本次未修改日常服务的系统提示、模型或后端。**

## 结论

本批探针不支持上线候选提示。给 Qwen3-4B 增加一串项目名，并没有提供可靠的项目知识：两道资源约束题在词表开启的两种条件下，都出现模块归属或功效缺乏依据的问题。关闭词表后这些特定项目名错误没有出现，但回答仍有其他事实错误，也没有建立回答质量评价步骤。不能据此宣称“去掉词表就解决模型能力问题”。

一般性“尊重前提、不要混淆模块”约束未稳定改善这些失败。代号纠正保持正确，说明不能把所有任务笼统归为模型无法理解。后续若研究项目知识注入，应对照有来源的角色定义或检索证据，而非继续扩充裸名词表；仍须另行验证，当前没有把这一设想写成已实现收益。

## 预先固定的设计

- 输入、条件和 rubric 在运行前提交为 `242fd2c`；完整输入见[清单](benchmarks/2026-10-16-prompt-ablation-input.json)。四个原始失败/控制题加四个相关措辞变体，属于**四个任务族、八道题**，不是八个独立领域。
- 2×2 条件：baseline（无词表、无前提约束）、domain（有词表）、premise（有前提约束）、domain_premise（两者都有）。基础系统提示、约100字要求、当前问题和256 token预算保持一致。
- 领域词表包含 ASR、LLM、TTS、Pipecat、MiniCPM-o、DINet、FlashHead、StreamingTalker 等词；前提约束不直接提供题目答案。每道题的条件先后轮换，各条件位置总体平衡；这不是随机化，同一任务族原题与变体顺序相同。领域因素代表整个提示块，不能拆成单个术语的效果。
- Qwen3-4B，NF4，`do_sample=False`、`enable_thinking=False`。32次正式流式HTTP请求，另1次短预热。确定性请求不靠多次重复扩大质量样本量。
- 运行前逐条检查应用无活动会话、模型ready且不busy；未重启或改配置。准入检查与提交之间仍有竞争窗口，HTTP409会作为失败停止并保留记录。
- 当前监听进程对应的 `llm_server.py` 与仓库文件逐字节一致，SHA256及解码配置见[运行证据](benchmarks/2026-10-16-prompt-ablation-runtime.json)。该核对在采集后完成；不把模型路径名当作权重文件哈希。

## 按任务审查

以下为助手逐条文本审查，并经独立助手复核；**不是人类盲评，也不是通用模型排行榜**。每条观察见[审查记录](benchmarks/2026-10-16-prompt-ablation-review.json)。

| 范围 | 观察 | 对结论的限制 |
| --- | --- | --- |
| 架构比较原题，4条件 | 4/4仍把级联直接描述为高延迟、端到端为低延迟 | 一般前提约束未解决无条件架构优劣判断 |
| 架构比较变体，4条件 | 4/4不再直接断言端到端必然更快；但4/4把模块耗时直接相加 | 变体题本身明确禁止该断言；不能归功于候选系统提示。简单求和未限定串行实现、未考虑流式重叠，另记事实局限 |
| 排障题，8回答 | 明确检查系统提示/指令冲突0/8；明确隔离重放模型0/8 | 泛泛说“检查回答逻辑”不计为独立模型测试 |
| 排障原题，4回答 | baseline与premise共2/4重新检查已给定正确的ASR | 添加前提约束并未阻止重复排查已排除原因；词表组避免此项也不等于排障完整 |
| 资源约束题，8回答 | 明确建立回答质量测量步骤0/8 | 大部分建议优化资源或速度，缺少改善答错问题的验证闭环 |
| 资源约束题中的词表组，4回答 | 4/4有模块归属或功效缺乏依据的问题：DINet当ASR共3条、FlashHead当量化1条、StreamingTalker被赋予整体推理/准确性或内存改善功效2条 | 错误类型可重叠，不能将计数相加作为失败回答数；只说明这组受控输入的现象 |
| 资源约束题中的无词表组，4回答 | 未出现上述指定项目名错误，但存在把训练技巧用于推理、FP16笼统称量化等问题 | 关闭词表组不是“质量通过组” |
| 两道代号/预算更正，8回答 | 8/8采用最新值，每条件2/2 | 仅为简单上下文更正控制，不代表复杂推理或语音识别合格 |

没有给出“整体正确率”：原rubric覆盖取舍与步骤，部分事实缺陷是在逐条审查时额外发现，不能用事后变更的评分要求制造统一榜单。只按明确失败类型与分母报告。

## 传输与耗时

32/32正式请求无HTTP/解析/worker错误，文字增量与最终文本一致；输入与每次请求的哈希均复算通过。这里只证明本次文本请求成功结束，**接口没有返回生成token数或finish_reason，不能据此确认EOS或排除预算截断**。

| 条件 | 正式请求 | 首个非空文字中位数 | 请求总耗时中位数 |
| --- | ---: | ---: | ---: |
| baseline | 8 | 55 ms | 1.320 s |
| domain | 8 | 55 ms | 1.300 s |
| premise | 8 | 55 ms | 1.167 s |
| domain_premise | 8 | 77 ms | 1.402 s |

计时从客户端发出HTTP请求开始，首文字时间以接收非空NDJSON文字为准。表内混合了短纠正题和复杂问题，输出长度不同；没有做重复负载实验或显著性检验，不将更短回答导致的耗时下降归为推理加速。这里不含ASR、TTS、数字人、真实麦克风与扬声器，也不是端到端语音延迟。

## 复现

使用已部署且空闲的本地 `/health`、`/generate` 服务，应用健康接口需报告 `active_sessions`。脚本默认使用本项目本地端口，也可通过 `--llm`、`--app`指定部署者地址。

```bash
python docs/benchmarks/2026-10-16-run-prompt-ablation.py \
  --output artifacts/prompt-ablation/reproduction.json
```

脚本拒绝覆盖现有输出，每条请求即时原子落盘，保留错误与中止状态。除了真实33次请求，还用隔离模拟验证了会话占用时不生成、坏JSON响应保留失败、HTTP EOF不冒充模型EOS、已有记录不被覆盖。模拟验证不计入模型成绩。

[原始流式结果](benchmarks/2026-10-16-prompt-ablation-results.json)保留完整回答、块时间与失败字段；[采集脚本](benchmarks/2026-10-16-run-prompt-ablation.py)可重复执行。硬件负载、依赖与权重内容不同可能改变输出或耗时；本记录不宣称跨机器严格复现。

## 对阶段目标的影响

这是第四阶段的一个范围明确的负面消融结果，补上“名词提示偏置”这一缺失控制。MiniCPM服务本轮不可达，未在其上做同样对照；这些结论不外推MiniCPM。没有替换已部署策略。

第一阶段的人工动态质量、人工转写与物理声学测量仍未完成；空白GPU主机完整部署和广泛真人输入也仍待验证。这份实验不能关闭这些门槛，更不能据此宣称达到SOTA。

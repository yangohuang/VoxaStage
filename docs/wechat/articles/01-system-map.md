# 做一个能听、能说、能行动的数字人，需要哪些模块？

- 摘要：把语音识别、大模型、语音合成和数字人模型连起来，只是起点。真正困难的是让工具、声音和画面遵守同一个话轮：用户改口后停止旧任务，播放结束后正确记忆，切换形象时复用对话能力。本文用 VoxaStage 的实际结构，拆解这套实时系统的职责与边界。
- 封面主文案：让数字人真正进入对话
- 封面副文案：语音 · Agent · 形象，三层怎么协作
- 阅读前置知识：知道大模型能生成文本即可；不要求了解数字人训练。
- 对应代码版本：`dd44878`。本文描述该版本源码与已记录验证，不保证某台演示机器此刻运行同一配置。

你对着麦克风说：“检索项目文档，介绍一下支持哪些数字人驱动。”屏幕上的角色开始回答。说到一半，你补了一句：“停一下，只介绍三维的。”

这段交互适合作为验收场景。它考察的不只是识别是否准确、口型是否漂亮，还包括几个容易被演示掩盖的问题：旧检索结果晚到怎么办？刚生成但没播放的声音要不要继续排队？下一轮模型是否会误以为用户已经听完前面的介绍？

VoxaStage 是一个本地优先的实时语音与数字人交互项目。它把两类语音后端、真实工具和三种形象驱动接进同一套会话。本文先给出系统地图，再说明已经走通的部分、仍然存在的缺口，以及为什么需要这样的拆分。后续文章沿着这张地图逐层展开。

## 一、把“会说话”拆成三层职责

第一层是对话后端，负责理解输入、组织回答和产生声音。它决定“听到了什么、准备说什么”。第二层是会话与 Agent 编排，负责工具执行、话轮切换、取消和上下文。它决定“这件事属于哪一轮、现在还应不应该继续”。第三层是形象呈现，把声音对应的视频或网格交给浏览器。它决定“角色如何动、什么时候展示”。

这些职责经常被混在一起。有人把 Pipecat 和端到端语音模型当作互斥选项，实际二者处于不同层：Pipecat 提供处理器管线和会话相关机制，模型负责推理。级联和端到端描述的是模型链路，不能据此把编排框架叫作第三种模型范式。

![三层职责：对话后端、会话编排、形象呈现](../assets/01-layers.png)

*图 1：职责示意，并非严格调用顺序。编排层协调对话后端和媒体输出；图中的模型能力分别来自对应上游项目。*

划清边界后，更换角色通常不需要重写问答逻辑；改变语音模型时，也可以尽量复用播放器与生命周期处理。这里的“复用”仍然需要协议适配：不同后端的采样率、分块方式、时间戳和取消行为不会自动一致。

## 二、同一个会话，两条语音路径

级联路径依次使用 ASR 识别、大模型生成文本、TTS 合成声音。中间结果比较容易观察：识别错了，可以检查转写；识别正确但答非所问，可以核对实际输入大模型的消息；文字正常但声音异常，再检查合成环节。

VoxaStage 的另一条路径接入 MiniCPM-o，让模型直接理解语音并生成语音，还可以结合按需提交的图片。这保留了端到端多模态模型的接入方式，但不能据此保证识别、推理或自然度必然优于级联。更不能只比较模型首个输出，就宣布整个系统延迟更低。

两条路径在这个版本里仍然依据话轮边界处理输入。级联的 ASR 按 VAD 分段，文本和音频可以增量输出；端到端路径也由应用管理话轮。流式输出、可打断交互和原生全双工是不同能力，本文只讨论已有实现，不把它们合并成一个标签。

## 三、让对话真正触发工具

一个常见误解是：回答里写着“正在查询”，就代表系统已经执行查询。真正的工具调用必须有明确的请求、运行状态和返回值，随后才能把结果交回模型继续回答。

当前级联路径接入文档检索、文档读取、计算和服务状态检查四类工具。执行器限制可访问的文档和操作范围，并向页面呈现执行中、完成、失败或取消。它使用适配本地模型的受限文本协议，不能直接等同于模型原生提供 function calling。

工具会把一次问答拉长成异步过程。用户可能在检索完成前改口，服务也可能在取消之后才返回。这时“拿到结果”不再等于“应该采用结果”。结果必须仍然属于有效话轮，才可以进入后续回答；旧任务不能因为晚到就重新接管对话。

MiniCPM-o 路径尚未接入同一套工具调度。对外展示时，这个差异应当直接说明，否则用户很容易把同一页面理解成所有后端能力完全相同。

## 四、三种形象，共用一套交互约束

DINet 与 FlashHead 在当前集成中输出二维视频；StreamingTalker 输出三维人脸网格。前两者让浏览器播放图像序列，后者需要浏览器更新顶点并渲染。三种驱动提供不同的呈现方式，具体模型原理和资源要求将在各自文章中解释。

无论输出是什么形式，都要回答相同的问题：这一帧属于哪段声音？声音实际播放到哪里？数据来得太快时如何限制排队？被打断的旧帧是否还允许展示？VoxaStage 围绕浏览器的音频播放时钟调度对应画面，并通过有界队列和迟到数据过滤维持播放秩序。

有界队列能限制积压，却不能创造算力。推理持续慢于播放，仍然可能发生缺帧或等待；浏览器进入后台也可能改变调度。因此，协议设计、模型吞吐和最终感知质量需要分别验证。

声音与形象也是两个配置维度。参考音色决定合成声音，渲染器决定角色外观。项目中的男女声配置是音色映射，不代表合成了展示人物本人的声纹。

## 五、一次打断，为什么需要全链路响应

假设用户在介绍过程中要求改讲三维驱动。页面先停止旧播放、清理排队的媒体；服务端使旧话轮失效并尝试取消相关任务。之后即使旧工具、模型或渲染器继续返回数据，也要经过有效性检查，不能直接进入新话轮。

![打断后需要同时处理播放、任务、结果和上下文](../assets/01-lifecycle.png)

*图 2：一次打断涉及四类工作。取消任务和拒绝旧结果需要配合，不能把发送取消指令当成所有底层计算已立即停止。*

上下文还会带来另一种隐蔽错误。假如模型已经生成五段话，浏览器只播放了两段，就把五段全部放进历史，下一轮模型可能说“正如刚才介绍过”，但用户其实没听到。

当前实现依据浏览器确认播放的完整语句段保留模型历史，未确认部分记录为中断。显示层可以保留生成记录，让用户看到发生了什么；模型上下文则采用更保守的播放记录。这是段级机制，还不是逐词对齐，也不能证明声音确实被人听见。

这样的处理让“对话状态”不再只等于文本列表，而是同时关联任务归属、播放进度和有效话轮。第三篇会专门拆解这条链路。

## 六、哪些是项目贡献，哪些来自上游

模型能力来自上游：语音识别与文本模型、IndexTTS、MiniCPM-o，以及 DINet、FlashHead、StreamingTalker。Pipecat 提供编排基础，Three.js 提供浏览器三维渲染能力。VoxaStage 没有据此宣称完成这些模型的预训练或原创网络设计。

本项目主要做服务适配、双后端与三驱动组合、可取消工具执行、旧结果隔离、播放确认上下文，以及统一的媒体生命周期和验证工具。工程贡献是否成立，要看这些约束在真实故障与交互里是否有效，不能只靠架构图上多画几个模块。

例如，现有数字人适配基线记录了三驱动共 54 次请求，并保存了另一组 45 次输出捕获。这些材料可以支撑协议和输出检查，却不能替代人工口型评价。合成输入、虚拟设备或浏览器调度记录，也不能直接证明物理麦克风到扬声器的完整延迟。

## 七、从哪里开始复现

阅读仓库时，先看首页的来源与许可，再看部署说明和演示路线。应用安装与模型部署是分开的，权重、人物模板、参考音色和运行录音不随源码分发。先确认依赖服务可用，再进入浏览器测试，能避免把服务未启动误判为对话逻辑故障。

建议先验证一个简单的计算请求，再在回答期间打断并换一个问题，最后切换不同驱动检查媒体恢复。它们分别考察工具执行、话轮失效和播放器复用，比只看角色能否张嘴更接近系统的关键约束。

目前仍有需要继续补齐的部分：更广泛的真人中英混合语音、动态口型与音色评价、物理回声和延迟，以及独立空白 GPU 环境的完整部署。连续视频理解、完整卡通动作和决策模型也不能提前算进当前成果。

这套系列将用已验证的实现和保留下来的失败记录解释这些问题。下一篇先比较两条语音路径：当它们进入同一个应用，哪些部分可以共用，哪些差异必须保留？

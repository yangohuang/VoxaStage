# 用户说“停一下”之后，语音 Agent 还要处理什么？

摘要：一句“停一下”会同时触及工具执行、模型生成、音频播放和会话历史。本文沿着 VoxaStage 的真实实现，解释取消为何需要配合迟到结果隔离，播放确认如何影响下一轮，以及当前机制距离理解用户意图的语义打断还有哪些边界。

封面主文案：“停一下”之后，发生什么？

封面副文案：任务取消 · 旧结果隔离 · 播放确认

阅读前置知识：了解异步任务和语音链路的基本概念；建议先阅读本系列第 02 篇。

基准版本：`dd44878`

## A 播完了，B 只说了一半

用 A、B、C 表示助手依次生成的三段解释。浏览器已经播完 A，B 说到一半，用户打断了，C 还留在队列里。下一轮该把哪些文字交给模型？保存全文，模型可能把没播出的步骤当成双方已经讨论过的内容；全部删除，刚刚播完的 A 又丢了。

这个示意把语音对话里几种“完成”分开了。模型已经生成完，合成服务可能还在工作；音频已经发到浏览器，用户可能还没听到。即使扬声器安静下来，旧检索也可能仍在等待返回。一次打断会影响这些同时进行的工作，仅靠播放器的停止按钮，无法决定下一轮该保留什么。

VoxaStage 在 Pipecat 的管线与中断基础设施上，补充了工具运行时、轮次隔离、媒体会话和播放历史。基础模型负责识别、生成或合成，应用与播放器则需要共同维护打断后的状态。当前实现对 A、B、C 的处理比较保守：保留确认播放完的完整语句段，为后续未确认内容记录中断。要让这个处理可靠，先得防止旧任务把内容继续送进来。

## “执行中”刚显示出来，任务就可能过期

设想助手正在检索项目文档，用户改口，让它先算一个数。页面刚收到工具“执行中”的状态，还没有显示结果。这里有一个容易被忽略的间隙：异步生成器把状态交给消费者时，会暂时让出控制权，取消恰好可能发生在这个间隙。恢复执行后，如果直接启动检索，就会让一个已经失效的任务开始干活。

运行时因而要在真正等待操作之前，再检查当前轮次是否有效。检查不能只放在函数入口；经过一次等待，原本有效的状态就可能改变。工具返回后、结果准备进入回答时，也要核对它仍然属于当前轮次。

这些工具确实会执行函数。目前级联链路支持项目文档检索、白名单文档读取、算术计算和配置中的服务状态查询。检索提供文档标识与片段，读取限制正文长度，计算采用受限语法，状态查询只返回筛选后的可展示字段。工具目录和参数检查限定了它能做什么，没有开放任意命令、任意文件路径或任意网址执行。

调用来自模型增量输出里的受限文本协议。解析器把工具名和参数提取出来交给运行时，普通回答继续流向语音合成，调用标记不应被读出来。它不是模型原生函数调用。符合特定格式的明确项目文档请求还会触发预检索，但这条规则范围有限，不能据此说每个问题都会先查文档。MiniCPM-o 的端到端语音与可选视觉路径目前没有接入同一套工具调度。

工具结果会作为外部数据，连同原问题送回模型。这个标记说明结果的来源和信任边界，不能保证模型绝不会误用其中的内容；回答是否忠实于检索结果，仍然要对照文档检查。

运行时给等待设置了预算：默认最多三次工具迭代，单个工具八秒超时，整轮六十秒，并限制输出大小。这些数字是默认配置，不是测得的服务速度。单个工具超时后，错误可以作为数据交回模型，让它说明未取得结果；整轮截止时间仍然有效。页面上的执行中、完成、失败和取消状态描述的是工具任务，“工具完成”不能顺手改写成“回答完成”，更不代表已经播放结束。

## 旧结果返回时，取消请求可能早已发出

发出取消之后，下游未必立即停止。底层操作可能还在清理，甚至可能捕获取消异常，稍后照常返回。此时新问题已经进入系统，旧结果再有效，也不该参与新回答。

工具运行时为每轮保存独立状态。新轮次开始时，旧轮次失效，正在等待的操作收到取消请求；返回结果还要通过当前轮次检查，过期结果不能继续进入正常回答路径。新轮次也不必等一个拒绝取消的旧操作彻底退出，才能开始工作。源码里的受控测试就安排了这种工具：它不立即响应取消，等新轮次继续后才返回，用来检查迟到数据是否被隔离。另有测试覆盖报告“执行中”后立刻取消、超时后继续新轮次的情况；这里依据的是测试代码，没有重新运行在线实验。

媒体也存在相同的竞态。后端正要发旧音频，另一边正在重置会话，如果两边只各自改状态，旧媒体仍可能越过重置消息到达浏览器。会话因此在与发送消息共用的锁内切换媒体轮次编号、清空片段队列并发送重置事件。浏览器时间线再检查编号，拒绝旧轮媒体。

检查还得跟着异步工作走。图片开始解码时可能属于当前轮，解码结束时会话却已经换了。完成回调不能因为终于拿到画面就直接显示，仍需检查当前状态。文字和合成音频也携带轮次，延迟抵达的旧合成结束或中断事件，不能误结束、误取消新回答。

![打断后的播放、任务、旧结果与历史处理](../assets/03-cancellation.png)

*图 1：打断后的几项职责并发配合，不表示固定顺序或耗时。*

浏览器停止播放后会清理待播音频和画面，让角色回到相应待机状态。取消负责减少旧工作，轮次核验决定返回内容还能否使用；后者管的是输出归属，不能证明所有推理和资源都已瞬间停止。当前工具属于只读或计算型，这些处理也没有撤销任意外部副作用的能力，不能直接当作转账或下单的回滚方案。

## 播放回执只能沿着连续的音频往前走

再看开头的 A、B、C。服务端需要先知道自己实际发了多少音频，才有办法判断浏览器的回执是否可信。当前实现记录已发送的累计采样数，把完整文本段关联到对应音频的结束采样位置。音频自然播放结束后，浏览器才报告进度，服务端核查轮次、片段和采样上界，并要求进度单调增加。

单调增加还不够。假如前一个片段没有确认，后一个片段的回执先到了，历史不能直接跳过去；中间缺口仍然意味着一部分音频没有播放证据。确认必须连续，文本标记也要对应生成文字的前缀，满足这些条件的完整文本段才会进入已确认历史。生成量、排队量和发送量都不能替代这个判断。

浏览器强制停掉音频时，也不能把停止事件当作自然播放结束。否则用户打断 B 的动作，反而会生成一份“B 已经播完”的错误凭据。声音虽然停了，错误历史却会影响下一次回答。前端只在当前音频自然结束时报告进度，打断后的清理不会用强制停止冒充正常播放。

![生成文字与确认播放历史的差异](../assets/03-playback.png)

*图 2：A 完整确认，B 中断，C 未播；模型历史只保留 A 和中断标记。*

于是，在这个示意里，模型历史保留 A，B 和 C 对应的后续内容被标为未确认播放。B 即使播出了大半，也不会按播放时长比例截取几个字。项目没有可靠的逐词时间对齐，采样位置只能支持当前的完整语句段确认，不能凭空变成逐词证据。

代价是下一轮可能重复 B 里用户实际听过的部分。比起把未听到的步骤当成共同背景，这种保守选择更符合现有信息。回执本身仍只是软件播放证据，无法判断用户是否静音、有没有戴耳机、注意力是否在回答上，更不能证明用户理解了内容。

页面展示记录可以继续保留生成全文、确认文字和中断状态，方便回看；模型上下文使用保守的播放历史。这两份记录承担不同用途，无须为了看起来一致，就把全文都交回模型。保存快照时，即使话轮还在运行，也按当前已确认内容记录；取一次快照本身不会强行结束活跃话轮。

## 保存尚未落盘时，连接也可能被取消

打断之后关闭页面，再载入会话继续，是另一处容易误把异步工作当成同步操作的地方。本地会话支持新建、载入和删除，恢复时绑定原来的对话后端与角色。保存层通过版本检查、文件锁和原子写入处理并发保存，防止记录和版本失配。

应用还需要处理等待保存的任务被取消的情况。后台磁盘写入不会因为等待方收到取消就自动停止；如果此时提前释放会话保存锁，后续保存可能在版本号尚未更新时进入。因此应用要等待后台写入完成，把保存结果和版本号更新好，再释放这把锁。这里的取消语义与工具很相似：调用方不再等待，不等于底层工作已经消失，但保存必须完成必要的状态收尾。

恢复带回的是上下文。已经取消的检索不会重新执行，旧媒体队列不会重新播放，新连接会建立新的播放生命周期，再根据保存历史处理后续输入。这是一套本地受限的会话存储，并不是能从断点接着跑的多租户持久任务系统。

端到端历史还可能含有音频和图片。代码分别限制历史轮次、输入音频与图片数量，较早内容可能被裁剪；恢复的图片会重新分配标识空间，避免与新浏览器连接的图片编号冲突。加载这些数据不等于永久记住所有细节，也没有把单次图片输入扩展成连续视频理解。

至于标题里的“停一下”，当前自动语音打断主要由 VAD 检测到新说话触发，手动按钮和新文字输入也能触发。系统可以先停住旧输出，再知道用户说了什么。它尚未完成对打断意图的语义判断，也不是原生全双工。

一句“嗯”、背景人声、纠正上一句话和要求换个目标，需要不同的后续处理。何时继续听、何时恢复原回答，还需要交互策略和真实麦克风、回声环境的验证，本文没有新增这些验收或打断延迟数据。检查当前实现时，可以先沿着具体时序追问：新问题已经开始，旧工具才返回，会发生什么；B 强制停止后有没有被误记为播完；保存被取消时，版本号何时更新、锁何时释放。这些问题都能回到代码里的等待点和消费入口逐项核对。

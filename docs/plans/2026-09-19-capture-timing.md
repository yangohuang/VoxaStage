# 浏览器采集边界计时

延续已确认的基线路线，补足PCM传输之前的浏览器采集观察。选择默认关闭的worklet元数据：比仅在WebSocket发送处打点更接近采样边界，又不需要替换现有重采样与传输。物理麦克风声学延迟没有校准，不声称测得。

## 设计与步骤

1. `avatar-web/mic-worklet.mjs`通过`processorOptions.captureTiming`启用诊断，普通模式继续发送ArrayBuffer。诊断模式在同一缓冲外包裹采样率、输出样本区间、对应输入帧坐标、生成该包的处理块范围；字节内容保持相同。
2. 输入帧坐标以AudioWorklet的`currentFrame`为原点，重采样位置按采样率比值计算。若中途缺输入或块不连续，创建新的连续片段；跨越断点的PCM包映射标为无效，后续完全位于新片段的包恢复有效。不改变PCM、不拼接出伪造的连续采样时间。
3. `Microphone`增加可选`captureTiming`参数；主线程解包后仍把PCM作为回调第一个参数，诊断元数据作为第二个参数。记录`performance.now()`前后夹住`context.currentTime`读取。两个时钟的关联是观测锚点，包含主线程调度与音频量子精度，不能当物理采集时刻。
4. 先写并运行失败测试：不同输入采样率下诊断与默认PCM一致、区间连续、输入断点、关闭后迟到消息；实现后验证。真实Chromium使用文件虚拟麦克风走getUserMedia→MediaStreamSource→worklet→回调→本地WebSocket路径，保存代码和输入摘要，明确不是物理设备测试。
5. 更新采集计时文档、阶段路线、源码导出验证和私有草稿PR。动态质量评审另做，不以计时测试代替。

不使用`getOutputTimestamp`冒充麦克风输入时间；它描述输出设备的渲染位置。采样帧位置精确可关联，跨时钟换算和声学输入输出边界分开报告。

真实浏览器调查修正：最初采用“遇到缺口后永久无效”，导致两个诊断请求所有包都无效。临时插桩观察到启动处理块为`[0,128] → [384,128] → [512,128]`（帧位置、块长），确有256帧断点。保留这次失败；先补充断点包失效/后续片段恢复的失败测试，再采用分段映射。没有丢弃或补造音频来让测试通过。

已验证：最终三配置各260包传输一致；两个诊断配置各259包有效、1包跨断点无效。新增12项测试、前端回归与独立审查通过。见[结果与使用方式](../CAPTURE-TIMING-BASELINE.md)。

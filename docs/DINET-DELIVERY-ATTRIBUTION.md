# DINet供帧间隔归因 · 2026-09-19

前一轮固定PCM浏览器基线在三次DINet请求中重复观察到调度空隙。本轮增加可选诊断回调，默认不开启，发送与播放策略不变；没有修改原生模型服务。

## 固定输入与观察

同一条2.432秒中文PCM，预热一次、正式三次，完整输出均通过原音频校验。每次61帧，记录音频块发送、帧头/帧体取得、编码调用起止和配对媒体交付，同一进程单调时钟。

| 正式轮次 | 原生帧头19→20间隔 | 上一配对媒体→帧20头 | 帧20体接收 | 帧20编码墙钟 | 配对媒体19→20间隔 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 264.5ms | 248.4ms | 2.6ms | 12.3ms | 263.7ms |
| 2 | 266.8ms | 252.7ms | 1.9ms | 12.8ms | 267.6ms |
| 3 | 265.0ms | 250.8ms | 3.3ms | 12.5ms | 266.9ms |

约250ms的主要间隔出现在下一图像帧头交给适配器之前；本次帧体读取和编码墙钟明显较小。帧头标记在`recv`返回并解析之后，因此“上一配对媒体→帧头”也可能包含中间原生音频/控制消息处理，不能称作纯网络等待或GPU推理时间。编码墙钟包含线程池排队和恢复调度，不是纯CPU编码耗时。事件的`frame`是待交付输出索引；尾部被丢弃的补零帧可能重复该索引，不把它当作唯一原生帧号。

## 原生源码交叉检查

只读检查当前部署的原生WebSocket路由和worker：音频输入路由实际启动`audio_stream_consumer_realtime`。该消费者先快速处理五个200ms音频块，随后按“会话起点 + 已处理块数 × 0.2秒”等待，之后继续按该时钟消费。

这会在首次快速处理五块后等待接近1秒，而不是保持固定的输入提前量。在三次实测中，第六块音频早在4.6 / 10.7 / 4.8ms已从客户端发出，帧20头却在约1.03秒才被观察到。该边界与原生消费者的等待策略吻合，支持将其列为下一项受控实验变量；不能仅据此声称因果干预已经验证或模型已加速。

源码摘要：

- native worker：`95dbdd85b278176b4ad6d18aac629314c03b4f085bccbe15bbce0d1038dae504`，消费节奏定位568–578行。
- native WebSocket路由：`2f134a3b3b0d8026bfd8d355077fca793df68b0c60c823a8c7587c5118f48c88`，调用定位266–267、288–289行。

这是既有部署的自定义服务，不能泛化为DINet官方算法的问题。其源码、人物与权重不复制进本仓库。模型上下文及分批生成仍需要提前量；下一步应比较“保留有界提前量”的策略，同时验证队列、取消、长音频、首声与口型输出，不能直接取消所有限速。

## 复现

```bash
.venv/bin/python trace_dinet.py \
  --manifest artifacts/quality-inputs/cases.json --case zh-00 \
  --config runtime/avatar-config.json --rounds 3 \
  --output artifacts/dinet-trace \
  --deployment-label 'non-secret native revision / character alias / device / residency'
```

新输出目录内保存完整事件、输入/源码哈希与成功失败状态；不记录原始媒体或服务地址。`observer`是进程内可选诊断回调，不是从浏览器开放的参数。回调有少量开销，诊断数据不替代未插桩性能基线。

124项应用/评测Python测试通过。本轮新增适配器事件顺序、无媒体载荷、固定输入重复和异常隔离测试。机器记录见[分层事件](benchmarks/2026-09-19-dinet-attribution.json)。完整质量基线、语音打断与后续真实优化对照仍未完成。

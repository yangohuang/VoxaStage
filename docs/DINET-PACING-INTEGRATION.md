# DINet 原代理路径的节奏优化验收

2026-09-19，消费提前量已通过原代理、原 worker 生命周期和生产播放器对照，在当前本地部署保留 **0.4 秒**。源码导出的启动器仍要求部署者明确提供配置；不会替其他部署自动启用。此前的[隔离实验](DINET-PACING-EXPERIMENT.md)与本次集成分别记录。

## 改动与归属

原生消费者快速处理前五个 200ms 块后，按完整已消费时长等待，导致第 19→20 帧附近的供帧停顿。本项目的 [dinet-server](../dinet-server/README.md) 在内存中将等待目标减去有限提前量。模型推理、25fps 输出、心跳、代理、缓存和清理均来自既有服务；没有修改原生文件或模型权重。

启动器先检查原生 worker 和 WebSocket 服务的完整源码 SHA，仅支持已审计版本；配置范围为 0–0.8 秒，0 保持原等待公式。每个 WebSocket 消费者读取一次原子配置快照并记录配置 SHA，请求中途不变，浏览器不能指定提前量。当前每个 clip 新建连接，配置更新作用于后续 clip。

```mermaid
flowchart LR
  C[部署配置与版本校验] --> W[原 worker：等待目标减去提前量]
  W --> P[原代理]
  P --> A[原适配器：配对 PCM 与图像]
  A --> B[生产播放器：按音频时钟调度]
```

## 对照结果

原代理 API 共 17 次：1 次预热、6 次短句交错对照、4 次长片段/停顿对照、3 组取消与恢复。全部通过各自断言；完整请求的 PCM 与输入逐样本相同，取消请求只检查已收到前缀。17 次复用同一 worker，实际配置日志与期望 SHA 逐次匹配。

| 短句 API 指标（各 3 次，预热排除） | 0 秒 | 0.4 秒 |
| --- | --- | --- |
| 原生第 19→20 帧头间隔 | 263.5–293.1ms | 37.9–40.0ms |
| 最大配对媒体接收间隔 | 263.1–289.9ms | 44.6–57.5ms |
| 完整帧 / PCM 样本数 | 61 / 58,368 | 61 / 58,368 |

三次取消各收到 31 帧、前缀正确；后续请求均恢复为完整 61 帧。观察到代理空闲需 8.6–12.2ms，含关闭和状态查询，不是 GPU 内核取消时长。损坏配置真实请求约 15.2ms 后失败且代理空闲；此计时含失败、关闭与查询，修复配置后完整生成成功。这一故障与恢复检查单列，不计入上述 17 次。

最终浏览器运行另含 1 次预热和 10 次正式对照，复用原播放器。重启后仍逐次核对 worker 应用配置；此处不是与 API 轮次共用同一个进程。

| 浏览器输入 | 0 秒最大音频调度间隙 | 0.4 秒最大音频调度间隙 | 0 秒 / 0.4 秒实际展示帧数 |
| --- | --- | --- | --- |
| 2.432s 短句，3 次 | 165.3 / 138.7 / 117.3ms | 均未测到 >1ms 间隙 | 均为 61/61 |
| 9.728s 重复短句，1 次 | 154.7ms | 未测到 >1ms 间隙 | 243/244；243/244 |
| 5.008s 含停顿语句，1 次 | 154.7ms | 未测到 >1ms 间隙 | 126/126；125/126 |

全部浏览器轮次调度了完整 PCM 样本，结束后无待播音源和排队帧。**音频调度间隙消失不代表视觉零跳帧**：长片段两种配置都少展示一帧，停顿片段的提前量配置也少展示一帧。没有测量物理扬声器或评定口型准确度。

## 失败与回滚证据

- 前两次回滚预演分别发现容器挂载只读、容器命令未传递标准输入。就绪检查在修改服务前拦截；修正后把锁和状态放入容器可写目录，并检查写入内容 SHA。
- 第三次预演实际替换启动命令，再让独立看门狗到期：原 supervisor 配置 SHA 与代理加 4 个 worker 的运行状态均恢复。
- 正式 API 检查后，浏览器工具复用了已经关闭的调试会话，尚未播放即失败。该次总报告保持 `failed`，控制器实际恢复原命令和 5 个运行进程；不会把 17 次 API 通过写成整次部署通过。
- 改用独立浏览器会话后，只补跑此前未完成的浏览器检查。前置 API 报告 SHA 与相同部署源码 SHA 绑定，最终检查全部通过才结束回滚租约并保留 0.4 秒。

最终确认代理和 4 个 worker 运行、无活跃连接，原生两个文件 SHA 未变。部署时的独立看门狗已经正常结束，**不是常驻服务监控**。此前隔离实验关于独立回滚保障的表述也已更正：当时证实的是控制器退出清理恢复，独立看门狗是在本次预演中才得到验证。

## 复现与回退

1. 按[启动器说明](../dinet-server/README.md)校验已有服务版本，备份部署配置，在空闲时接管 worker 启动命令，保留原代理、进程数和环境变量。先配置 0 秒。
2. 使用[统一输入清单](AVATAR-EVALUATION.md)，记录 WAV、归一化 PCM 和源码 SHA。以 `trace_dinet.py --manifest <清单> --case <编号> --config <服务配置> --output <新目录> --deployment-label <标签> --rounds 3` 观察适配器与原生帧头事件。
3. 原子修改提前量，在相同 worker、输入、传输压缩设置和播放器缓冲下交错测试；以 worker 日志核对实际应用值。浏览器入口和记录方式见[固定 PCM 基线](FIXED-PLAYBACK-BASELINE.md)。预热、正式、取消、故障与恢复分开计数。
4. 回退策略时原子写入 0；撤销启动器则在服务空闲时恢复原 worker 命令并重启该组。每次核验代理心跳、连接数与实际应用日志。

[机器记录](benchmarks/2026-09-19-dinet-integration.json)包含输入/源码摘要、逐次帧头时间、浏览器音源调度/展示事件、配置摘要、失败原因和原始报告 SHA，可独立重算表中数值。部署控制器、浏览器脚本、回滚脚本及其 SHA 已在本地归档；机器路径、supervisor 配置、素材和模型地址不随源码导出。

这是单部署、固定交错顺序、小样本的媒体等待策略优化，不是模型算力提升。没有验证四 worker 并发、完整 30 秒 clip 或持续长会话；0.4 秒只是已测有效值，没有证明全局最优。单输入 61 帧内容完全相同的证据来自前次隔离实验，不能替代本次所有输入的感知质量验收。

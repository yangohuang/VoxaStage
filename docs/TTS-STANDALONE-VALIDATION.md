# 独立 TTS 环境、GPU 加载与真实服务验证

2026-10-16：两个独立 Python 环境按同一份154包哈希锁完成重建，分别通过27项协议与生命周期回归；RTX 4090 上的官方 IndexTTS 2.5 模型实际加载和退出释放通过。
随后使用上游公开参考音色启动独立 HTTP/WebSocket 服务，完成6次真实合成及2次断连恢复检查。
这些结果验证功能和单次时延，不代表发音准确、音色相似或口型质量通过。

## 固定输入与归属

- worker 源码检查点：`88620f9cf78c21f59e1e6226ffce31850a1ae311`。
- 上游源码：[`a371df7d0746a0ae7fdf075798b6b04e34a0132e`](https://github.com/index-tts/index-tts/commit/a371df7d0746a0ae7fdf075798b6b04e34a0132e)。模型、声码器及文本分段合成来自上游。
- Python 3.11.15，PyTorch/Torchaudio 2.8.0+cu128，Transformers 4.52.1；完整版本和发行文件哈希见[依赖锁](../tts-server/requirements-standalone.lock)。两个环境使用不同 Python 构建，不宣称系统镜像相同。
- [模型清单](../tts-server/model-files.json)覆盖四个固定上游版本、14个实际使用文件。远端传输后和加载前均重新检查完整 SHA256 与大小。
- VoxaStage 实现协议适配、单模型调度、取消清理、背压和连续重采样。上游按完整文本片段生成音频，尚不是语音 token 级流式生成。

## 安装失败与恢复

初始在线安装没有一次成功。两台机器分别在 `NCCL` 和 `cuSparse` 下载时遇到 TLS 响应提前关闭，安装器以1退出；没有将重试中的进程误判为完成。

保留原失败日志后，使用官方 PyPI 元数据选择与原锁匹配的发行文件，以8 MiB范围请求续传，并在完整下载后校验 SHA256。远端共补齐7个 CUDA wheel，本机补齐其中3个；其他依赖复用同一安装过程已验证的缓存。传输到远端的副本再次校验。

一次本机离线尝试仅加入 `--find-links`，仍选中了远端索引地址，因此失败。最终恢复顺序为：

1. 为缺失包生成指向完整本地 wheel 的临时清单，每项哈希必须出现在原锁对应包的版本段中。
2. 使用 `uv pip install --offline --no-index --no-deps --require-hashes -r recovery.lock` 安装这些精确文件。
3. 使用原完整锁执行 `uv pip sync --offline --require-hashes`，沿用原索引配置和同一安装过程的缓存。
4. 检查154个包的精确版本、发行包位置及 `uv pip check`，再运行测试和模型导入。

`recovery.lock` 是管理员根据本地已校验文件生成的恢复清单，不随项目附带机器路径。恢复没有降低哈希要求或更换依赖版本。这里验证的是既有机器上的全新虚拟环境，不等于空白 GPU 主机及系统依赖的完整安装通过。

## 公开参考音色的真实服务测试

参考输入来自 [IndexTeam 官方演示](https://huggingface.co/spaces/IndexTeam/IndexTTS-2-Demo/tree/b01840e8e4fd9753743a6d0466cd73ae1d634a68/examples)，固定版本 `b01840e8e4fd9753743a6d0466cd73ae1d634a68` 的 `voice_03.wav` 和 `voice_04.wav`。原始文件均为48kHz双声道，分别2.111秒、2.346秒；取声道均值并保存为单声道PCM16，不裁剪或重采样。来源、原始及准备后哈希记录在[服务验证数据](benchmarks/2026-10-16-tts-public-reference.json)。Space 元数据标注 Apache-2.0；仓库不分发参考音频或生成音频，也不将两个示例标为生产角色音色。

在前述环境中启动实际 worker，验证健康接口、音色列表及四消息 WebSocket 协议。服务首次 ready 为14.872秒，包含完整资源校验、模型加载和文本前端初始化；与前面的20.813秒构造探针属于不同进程、不同缓存条件，不能据此宣称加速。

| 请求顺序 | 公开音色 | 文本类型 | 首 PCM / 秒 | 完整接收 / 秒 | 输出音频 / 秒 |
| --- | --- | --- | --- | --- | --- |
| 1 | voice_03 | 中文 | 3.226 | 3.289 | 2.905 |
| 2 | voice_03 | 中英混合 | 0.807 | 0.875 | 4.147 |
| 3 | voice_04 | 中文 | 0.784 | 0.846 | 2.592 |
| 4 | voice_04 | 中英混合 | 0.724 | 0.792 | 3.753 |
| 5 | voice_04 | 提前断连后的恢复 | 0.568 | 0.628 | 1.907 |
| 6 | voice_04 | 收到首包断连后的恢复 | 0.558 | 0.614 | 1.988 |

所有完整请求返回成功结束帧及非静音24kHz PCM16，包长均不超过40ms。计时从第四条请求发送完成开始，到首个PCM包或结束消息；不包含音频播放、ASR或LLM，也不是模型内部纯推理耗时。每项只有一次观测，采样未固定随机种子，不报告P95或性能提升。首个请求包含首次推理开销，不能与后续请求当作相同条件比较。

两次真实长文本请求均在模型忙碌时关闭连接：一次在观察到 busy 后约0.3秒关闭、未调用接收；另一次收到首个二进制包后关闭。两次断连后立即发起的竞争请求均收到409，随后观察到空闲，各自的恢复合成都正常结束。进入空闲轮询后的等待分别为2.026秒、0.102秒，轮询间隔0.1秒；这不等同于精确的断连至释放耗时。第一种场景不能证明当时服务端尚未生成或缓冲音频；关闭套接字也不等于浏览器播放队列已清空。

测试完成后向专属 worker 发送SIGTERM，日志记录应用正常关闭，worker返回-15，验证控制进程退出0，未强制杀死。进程前后设备空闲显存均为18,801 MiB。日常服务没有切换。

## 实际客户端与浏览器组合验证

随后启动隔离应用，连接独立 TTS、既有 Qwen3-4B NF4 与 StreamingTalker 服务，未修改日常配置。已有 `LocalBackend.synthesize` 分别通过两个角色配置请求公开音色 `voice_03`、`voice_04`，均收到完整 PCM。角色配置名只是路由测试，不证明这些公开声音符合生产角色的性别或身份。

浏览器使用真实 Chrome、WebAudio 和软件 WebGL；通过点击连接解锁音频，再依次发送短句、播放中打断、恢复短句。观察脚本来自 `evaluation/browser-probe.js`，不替代音频源，不发送模拟播放确认。浏览器实际调度音频并渲染网格；没有使用麦克风。

| 场景 | 观察到首个渲染帧及音频调度 / 秒 | 收到媒体包 | 本轮渲染帧 | 浏览器音频源 |
| --- | --- | --- | --- | --- |
| 短句回复 | 1.217 | 73 | 73 | 73个自然结束，调度时长2.429秒 |
| 播放中打断 | 2.826 | 18 | 5 | 15个曾调度，其中11个被停止 |
| 恢复回复 | 1.820 | 57 | 57 | 57个自然结束，调度时长1.872秒 |

该时间从测试端发送文字前起算，采用轮询观察，包含调试协议开销；不同于上一节 TTS 首 PCM 时间，也不代表用户说完后的延迟。单会话三轮不能用于长期稳定性或 P95 结论。

调用打断后，立即观察到音频源数及待渲染帧数均为0；服务确认 generation 更新后仍为0。本地打断后、服务 reset 确认前仍到达1个旧媒体包，页面计数显示丢弃1包；确认更新后没有旧媒体到达，也没有为旧 generation 新建音频源。恢复完成后累计渲染135帧；断开后 idle 视频处于播放状态，音频和帧队列为空。浏览器没有记录运行时异常。

另核对已持久化的6条会话记录：第一轮与恢复轮的完整回复标记 `heard`，中断轮标记 `interrupted`、`heard_text` 为空，下轮模型上下文只带“后续内容未确认播放”的提示，没有把整段生成文本作为已听内容。这里的 `heard` 指客户端播放确认，仍不是物理扬声器听感证明。

专属 Chrome、临时应用、转发和 TTS 均已退出，没有强制杀进程。应用和 TTS 由 SIGTERM 结束，退出码为-15且日志记录正常应用关闭；远端监督进程退出0。设备空闲显存前后均为18,801 MiB，日常应用和3D服务复查空闲。数据、浏览器事件与音频源观察见[组合验证记录](benchmarks/2026-10-16-tts-browser-integration.json)。原始截图、音频及私有运行配置不随仓库分发。

复验时使用[独立 worker 启动方式](../tts-server/README.md)，为测试应用设置 `PIPECAT_TTS_URL` 和公开参考对应的 `PIPECAT_MALE_SPEAKER_ID`，使用独立会话存储目录。连接 StreamingTalker 后，依次发送“请只回复：你好，欢迎体验实时语音对话。”、“请用三句话介绍语音 agent 的工作过程。”，在第二轮播放期间打断，再发送“请只回复：已经恢复，可以继续对话。”。除播放状态外，必须核对当前三轮保存记录，不能只凭某个 `clip_end` 判断整轮完成。

## 真实模型的超时恢复与连续请求

为确定超时清理分支确实作用于真实模型，测试进程以同一个 `Engine` 启动两个回环服务实例：一个使用50毫秒期限，另一个保留90秒默认值。没有替换生成器、添加模拟阻塞或改变日常服务配置。连续请求前后各触发一次短期限超时：分别约55.107毫秒和51.282毫秒收到504，错误帧前均未收到PCM；模型仍忙碌，普通入口的竞争请求收到409。等待真实推理线程退出后，同一模型实例的恢复请求均成功。

该测试覆盖主动注入的50毫秒期限，不能当作90秒生产超时的复现。客户端在首个JSON帧后退出，因此仅凭本次真实测试不能断言错误帧后服务端从未尝试发送音频；发送取消的细节仍由代码审查和CPU负例补充验证。

同一进程在两次超时之间完成30个顺序请求，交替两种公开音色和三种固定文本（中文短句、中英术语、含列表的句子）。全部返回成功结束帧及非零PCM，累计输出99.333秒音频，批次耗时25.966秒。各次首PCM为0.613–0.923秒，均在首次超时恢复预热后测量；未固定采样随机种子，不报告P95或性能提升。每次等待线程退出后，存留任务列表最多1项、存活推理线程为0。

这30轮后，进程RSS相对首个完成请求增长118,988,800字节（113.48 MiB）；相对序列开始前增长133,754,880字节。RSS包含模型、两个ASGI服务、测试HTTP/WS客户端和累计结果字典，不能视作独立worker净占用，也不能据此断言泄漏或无泄漏。逐轮显存与RSS、超时/恢复结果及进程退出记录见[原始测量摘要](benchmarks/2026-10-16-tts-timeout-sequence.json)。这是一轮约26秒的连续请求检查，不是长会话验收。

### 内存增长的限定诊断

针对上述RSS变化，保留原结果，另启一次同样配置、120次顺序请求的诊断。在模型加载及首次超时恢复后开启 `tracemalloc`，逐次记录Python跟踪分配、进程RSS与PyTorch显存；末尾分别执行 `gc.collect()` 和 glibc `malloc_trim(0)`。这些操作只在验收脚本中使用，未加入服务请求路径。

120次请求均完成，末尾再次注入超时并恢复成功。带跟踪的序列耗时468.394秒，不能与未跟踪的30轮作吞吐对比。逐次等待后存活推理线程始终为0、任务列表最多1项。

| 采样点 | RSS / 字节 | PyTorch 已分配显存 / 字节 |
| --- | --- | --- |
| 序列前、跟踪开始前 | 4,463,218,688 | 5,511,595,520 |
| 第1次请求结束 | 4,488,552,448 | 5,505,036,800 |
| 第120次请求结束 | 4,863,254,528 | 5,511,178,752 |
| GC前（已生成分配快照） | 4,864,237,568 | 5,511,178,752 |
| GC后 | 4,864,237,568 | 5,511,178,752 |
| `malloc_trim(0)` 后 | 2,850,172,928 | 5,511,178,752 |

GC回收1122个对象，但RSS未出现可见变化；`malloc_trim` 返回1，随后RSS减少2,014,064,640字节，约1.88 GiB。这说明采样时存在大量可归还的glibc空闲页，不能将全部RSS增长直接解释为存活对象泄漏，也不能证明所有泄漏均已排除。首末请求的Python跟踪分配分别约0.65 MiB和6.57 MiB，增量主要记录在WebSocket压缩分配；跟踪器不覆盖此前分配及全部原生库/CUDA内存，且本身也有开销。没有在关闭跟踪器后立即单独采样，因此不量化其独立开销。

结论限于该批次的功能与线程生命周期通过，以及存在可释放的分配器保留内存；没有据此加入逐请求GC、清空显存或强制内存释放“修复”。仍需分离真实worker与测试客户端、扩展输入和运行时长，才能评估持续部署的内存趋势。两轮测试进程均退出0，退出前后设备空闲显存均为18,801 MiB。数据见[120次诊断记录](benchmarks/2026-10-16-tts-memory-diagnostic.json)。

## 尚待验证

# 独立 TTS 环境、GPU 加载与真实服务验证

2026-10-16：两个独立 Python 环境按同一份154包哈希锁完成重建，分别通过27项协议与生命周期回归；RTX 4090 上的官方 IndexTTS 2.5 模型实际加载和退出释放通过。
随后使用上游公开参考音色启动独立 HTTP/WebSocket 服务，完成6次真实合成及2次断连恢复检查。
这些结果验证功能和单次时延，不代表发音准确、音色相似或口型质量通过。

## 固定输入与归属

- worker 源码检查点：`88620f9cf78c21f59e1e6226ffce31850a1ae311`。
- 上游源码：[`a371df7d0746a0ae7fdf075798b6b04e34a0132e`](https://github.com/index-tts/index-tts/commit/a371df7d0746a0ae7fdf075798b6b04e34a0132e)。模型、声码器及文本分段合成来自上游。
- Python 3.11.15，PyTorch/Torchaudio 2.8.0+cu128，Transformers 4.52.1；完整版本和发行文件哈希见[依赖锁](../tts-server/requirements-standalone.lock)。两个环境使用不同 Python 构建，不宣称系统镜像相同。
- [模型清单](../tts-server/model-files.json)覆盖四个固定上游版本、14个实际使用文件。远端传输后和加载前均重新检查完整 SHA256 与大小。
- VoxaStage 实现协议适配、单模型调度、取消清理、背压和连续重采样。上游按完整文本片段生成音频，尚不是语音 token 级流式生成。

## 安装失败与恢复

初始在线安装没有一次成功。两台机器分别在 `NCCL` 和 `cuSparse` 下载时遇到 TLS 响应提前关闭，安装器以1退出；没有将重试中的进程误判为完成。

保留原失败日志后，使用官方 PyPI 元数据选择与原锁匹配的发行文件，以8 MiB范围请求续传，并在完整下载后校验 SHA256。远端共补齐7个 CUDA wheel，本机补齐其中3个；其他依赖复用同一安装过程已验证的缓存。传输到远端的副本再次校验。

一次本机离线尝试仅加入 `--find-links`，仍选中了远端索引地址，因此失败。最终恢复顺序为：

1. 为缺失包生成指向完整本地 wheel 的临时清单，每项哈希必须出现在原锁对应包的版本段中。
2. 使用 `uv pip install --offline --no-index --no-deps --require-hashes -r recovery.lock` 安装这些精确文件。
3. 使用原完整锁执行 `uv pip sync --offline --require-hashes`，沿用原索引配置和同一安装过程的缓存。
4. 检查154个包的精确版本、发行包位置及 `uv pip check`，再运行测试和模型导入。

`recovery.lock` 是管理员根据本地已校验文件生成的恢复清单，不随项目附带机器路径。恢复没有降低哈希要求或更换依赖版本。这里验证的是既有机器上的全新虚拟环境，不等于空白 GPU 主机及系统依赖的完整安装通过。

## 公开参考音色的真实服务测试

参考输入来自 [IndexTeam 官方演示](https://huggingface.co/spaces/IndexTeam/IndexTTS-2-Demo/tree/b01840e8e4fd9753743a6d0466cd73ae1d634a68/examples)，固定版本 `b01840e8e4fd9753743a6d0466cd73ae1d634a68` 的 `voice_03.wav` 和 `voice_04.wav`。原始文件均为48kHz双声道，分别2.111秒、2.346秒；取声道均值并保存为单声道PCM16，不裁剪或重采样。来源、原始及准备后哈希记录在[服务验证数据](benchmarks/2026-10-16-tts-public-reference.json)。Space 元数据标注 Apache-2.0；仓库不分发参考音频或生成音频，也不将两个示例标为生产角色音色。

在前述环境中启动实际 worker，验证健康接口、音色列表及四消息 WebSocket 协议。服务首次 ready 为14.872秒，包含完整资源校验、模型加载和文本前端初始化；与前面的20.813秒构造探针属于不同进程、不同缓存条件，不能据此宣称加速。

| 请求顺序 | 公开音色 | 文本类型 | 首 PCM / 秒 | 完整接收 / 秒 | 输出音频 / 秒 |
| --- | --- | --- | --- | --- | --- |
| 1 | voice_03 | 中文 | 3.226 | 3.289 | 2.905 |
| 2 | voice_03 | 中英混合 | 0.807 | 0.875 | 4.147 |
| 3 | voice_04 | 中文 | 0.784 | 0.846 | 2.592 |
| 4 | voice_04 | 中英混合 | 0.724 | 0.792 | 3.753 |
| 5 | voice_04 | 提前断连后的恢复 | 0.568 | 0.628 | 1.907 |
| 6 | voice_04 | 收到首包断连后的恢复 | 0.558 | 0.614 | 1.988 |

所有完整请求返回成功结束帧及非静音24kHz PCM16，包长均不超过40ms。计时从第四条请求发送完成开始，到首个PCM包或结束消息；不包含音频播放、ASR或LLM，也不是模型内部纯推理耗时。每项只有一次观测，采样未固定随机种子，不报告P95或性能提升。首个请求包含首次推理开销，不能与后续请求当作相同条件比较。

两次真实长文本请求均在模型忙碌时关闭连接：一次在观察到 busy 后约0.3秒关闭、未调用接收；另一次收到首个二进制包后关闭。两次断连后立即发起的竞争请求均收到409，随后观察到空闲，各自的恢复合成都正常结束。进入空闲轮询后的等待分别为2.026秒、0.102秒，轮询间隔0.1秒；这不等同于精确的断连至释放耗时。第一种场景不能证明当时服务端尚未生成或缓冲音频；关闭套接字也不等于浏览器播放队列已清空。

测试完成后向专属 worker 发送SIGTERM，日志记录应用正常关闭，worker返回-15，验证控制进程退出0，未强制杀死。进程前后设备空闲显存均为18,801 MiB。日常服务没有切换。
